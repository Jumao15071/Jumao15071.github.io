Static Flicker-Door Zombified Piglin Farm: How It Really Works

Author: 橘猫sama · Edited 2026-10-18 11:33 cv53412179 · Entity Mechanics 中文
« Previous MCBE 部分掉落物及抢夺计算相关机制 Next » Raid Mechanics in Bedrock Edition

Zombified Piglins, formerly known as Zombie Pigmen (pigmen for short), are the zombified variant of Piglins in Minecraft.

In this article we will briefly introduce the mob mechanics of Zombified Piglins, then explain in detail why a pigman farm driven by rapidly igniting Nether portals works, and how current designs keep it efficient and stable.

Spawning

Let's have a quick look at how Zombified Piglins spawn:

Every naturally spawned Zombified Piglin has a 5% chance to spawn as a baby. Most of them spawn holding a golden sword, and 5% spawn holding a golden spear.

Zombified Piglins spawn in groups of 2–4 in the Nether Wastes and Crimson Forest biomes at light levels of 11 or below, but they cannot spawn on Nether Wart Blocks or Shroomlights.

Naturally spawned Zombified Piglins are awkward to farm. Nether portals, however, can spawn them too — and far more efficiently.

Each Nether portal block has a tiny chance to spawn a Zombified Piglin on every random tick:

Easy difficulty 12000 \frac{1}{2000}20001​

Normal difficulty 22000 \frac{2}{2000}20002​

Hard difficulty 32000 \frac{3}{2000}20003​

They spawn on the east or south side of the portal (depending on which way the portal faces), one block above the portal's lowest obsidian, and no block can obstruct this spawn.

In Bedrock Edition, the instant a Nether portal is lit, each portal block also gets one spawn attempt with the same chance — so repeatedly lighting and breaking portals can mass-produce Zombified Piglins.

Zombified Piglins spawned this way count against the mob cap, and they cannot be teleported to the Nether by the portal for 15 s.

Due to a bug, Zombified Piglins cannot spawn in Nether portals below Y=0. (MCPE-149718)

Also, 26.0+ has a 0.75% chance to spawn a special Zombified Piglin variant that cannot ride minecarts. (MCPE-236034)

Nether Portals

We will go straight to the practical video and explain the main principles behind it. The most widely used, stable and efficient pigman farm today is this one:

【Simple unload-resistant static flicker-door pigman farm】 by TK Minecraft

Why does this farm care about direction? Why must the portals straddle exactly 2 chunks and be 22×22? Why is the portal 22×21? Why does the igniter rig look like that? Why does the dispenser eject powder snow buckets at 2.5 Hz (0.4 s per cycle)? Let me walk you through it.

Why does the farm care about direction?

Because portals are lit by fire spreading from lava onto a flammable block, and the spread check order is:

East > West > Up > Down > South > North

That is why the video fixes the build direction first, to maximise the ignition success rate. (In practice, once the other five directions are walled off, the difference is small.)

Why must the portals straddle exactly 2 chunks?

Why must the portals straddle exactly 2 chunks? Would a bit more or less on either side not work? And could they span 3 chunks?

That brings us to the core of this article: pending ticks.

When a portal is created, every Nether portal block schedules one pending tick (pt; Java Edition calls it a scheduled tick). A single chunk can process at most 100 pending ticks per game tick (0.05 s).

Executing a pending tick calls function A (see the end of the article); its last two lines are the actual spawn attempt, so every pending tick runs that check.

First we need to know how a dispenser behaves: one full eject / retract cycle of a powder snow bucket takes 0.4 s in total:

0.1 s eject, 0.2 s cooldown, 0.3 s retract, 0.4 s cooldown

Given that the powder-snow flicker-door runs at 2.5 Hz (one cycle T = 0.4 s), a game tick is t = 0.05 s, and the maximum pending-tick throughput is N = 100 per tick, the total number of pending ticks C per flicker cycle is:

C=Tt×N=0.4s0.05s×100=800 (pending ticks)C = \frac{T}{t} \times N = \frac{0.4\text{s}}{0.05\text{s}} \times 100 = 800 \text{ (pending ticks)}C=tT​×N=0.05s0.4s​×100=800 (pending ticks)

Conclusion: each chunk can process 800 pending ticks in one 0.4 s flicker cycle.

All we can do is fill those 800 pending ticks with portal blocks — saturating pending ticks is exactly how you maximise the Zombified Piglin spawn rate.

[MinecraftBE] Pigman farm too slow? Too laggy? Here are the numbers!](https://www.bilibili.com/video/BV1Je411g72y)

Take the video as an example: two portals, each spanning 3 chunks (3/16/2) and 21 blocks tall. Lighting each portal once produces 672 pending ticks in the middle chunk. If the dispenser also runs at 2.5 Hz, the portal is open for 0.2 s and closed for 0.2 s; 400 pending ticks are consumed while it is open, and the remaining 272 are wasted during the closed half, because a closed portal cannot spawn anything.

If you stack a huge number of portals, each chunk still only processes a limited number of pending ticks per tick, so a flicker cycle that does not consume them all causes a pt backlog. The usual symptom: you run the farm for a while, switch it off, and the portals you left lit keep producing Zombified Piglins. Be careful here — a large pt backlog can cause irreversible damage to your save!

So, straight to the conclusion: more portals is not better — the pending ticks and the spawn output a chunk can handle are finite. To squeeze the most out of the spawn rate we split the portals evenly and keep each portal at 22×22 (400 portal blocks), precisely to control the pending ticks.

But don't forget: the farm above also runs at 2.5 Hz. Why doesn't it waste pending ticks?

The answer: observers, dispensers and droppers are all components affected by pending ticks — even lava is affected by pending ticks!

That means a clever, short pt backlog can shift when the dispenser fires, letting it eject the powder snow bucket, retract it, and have the lava ignite — all within the same second!

700 or more portal blocks' worth of pending ticks gives a perfectly built-up pt backlog, and such a flicker-door keeps the portal lit the entire time — not a single Zombified Piglin spawn is wasted!

But watch out: the dispenser consumes pt too, so you must remove one column of portals in the flicker-door's chunk, reserve (portals/2 rounded up) × 3 pt for the lava plus portals × 2 pt for the dispensers, and build nothing else in that chunk so the pt budget is not disturbed.

For 4 portals the reserved pt is: 4×2 (dispensers) + 2×3 (igniter)

The Igniter Rig

Now that the portal and the flicker-door are clear, one problem remains: the igniter rig.

You could craft flint and steel in a crafter and load it into a dispenser to light the portal, but that consumes materials. What ignites a portal automatically with no consumables? Lava.

In Bedrock Edition, every time lava triggers it first checks whether the block directly above it is air or a flammable block; if not, nothing is ignited. It then draws 10 random blocks from the 3×3×3 cube centred on the lava (independent uniform draws, repeats allowed). As soon as a flammable block is drawn, it checks that block's 6 orthogonal neighbours in the order +X, −X, +Y, −Y, +Z, −Z, and creates fire on the first air block it finds, ending immediately. Fire can therefore appear up to 2 blocks horizontally from the lava (except the four corners of the 5×5), or 2 blocks vertically (in which case the horizontal range is only 3×3); the flammable block itself must lie inside the 3×3×3 cube. Fire placement does not check for support or a valid fire location, so fire can float in mid-air.

Blocks such as crafting tables and trapdoors can carry fire spread, but they are not burned up themselves.

Even so, natural lava spread is slow. How do we make it faster? By activating the lava.

You may have heard that nc updates from high-frequency redstone components make fluids flow faster — cobblestone generators and moss machines use this a lot.

Before 1.21.70, fluids were split into static and dynamic fluids. A static fluid turns into a dynamic fluid when it receives an nc update and schedules 2 pt; a dynamic fluid turns back into a static fluid when its pt fires.

Fluid activation in a cobblestone generator is really this: a third party's pt is inserted between the fluid's two pt.
The rough timeline is:
0gt: the static fluid receives an nc update, schedules 2 pt to fire after n gt, and becomes a dynamic fluid;
ngt: the first dynamic-fluid pt fires, the dynamic fluid becomes static and tries to flow (lava additionally tries to ignite); the third party's pt fires, producing an nc update, so the static fluid schedules 2 pt to fire after n gt and becomes dynamic again; the second dynamic-fluid pt fires and the dynamic fluid becomes static, trying to flow and ignite. After this sequence the fluid is static again but has two extra pt scheduled n gt later. If the fluid receives an nc update within that n gt, it ends up with 4 pt, so it can flow twice in one cycle — repeat this and the fluid is activated. A dynamic fluid receiving an nc update produces no pt.

High-Frequency Signals

There is not much to say about high-frequency redstone: a 2.5 Hz flicker-door opens/lights the portal once every 8 gt. The dispensers must fire twice every 8 gt, i.e. once every 4 gt, so that is a 2 gt pulse every 4 gt — the fastest clock Bedrock allows. The igniter has to fire once every 8 gt, i.e. an 8 gt pulse every 16 gt. Never use an observer clock here, because observers are also affected by pt; the observer high-frequency part is only there to provide the initial short pulse.

To sum up: by designing the portals so that pt backlog builds up, and letting the dispensers eject and retract the powder snow bucket while the lava ignites within the same game tick, we have ourselves a static flicker-door pigman farm.

One more note: in 26.0+ there is a Zombified Piglin that cannot ride minecarts, so if you gather and kill with minecarts, add powder snow or turtle eggs as a backup kill method.

Source Code Analysis

A. What happens on every random tick of a portal block:

C++
void PortalBlock::tick (
    ::BlockSource&    region,
    ::BlockPos const& pos,
    ::Random&         random
){
    auto& block       = region.getBlock(pos);
    auto  portalAxis  = block.getState<TorchFacing>(VanillaStates::PortalAxis());
    auto  portalShape = PortalShape(region, pos, portalAxis);
    auto& dim         = region.getDimension();
    if (portalShape.isValid() && portalShape.isFilled()) {
        auto  portalRecord = portalShape.createRecord();
        auto& poralForcer  = region.getLevel().getPortalForcer();
        auto  dimId        = region.getDimensionId();
        if (!poralForcer.portalRecordExists(dimId, portalRecord)) {
            poralForcer.addPortalRecord(dimId, portalRecord);
        }
    }
    if (SpawnChecks::canSpawnPigZombieFromPortal(dim, random)) {
        PortalBlock::trySpawnPigZombie(region, pos, portalAxis);
    }
}

B. Spawn chance vs. difficulty:

C++
static bool PortalBlock::canSpawnPigZombieFromPortal(::Dimension const& dimension, ::IRandom& random) {
    auto& level     = dimension.getLevel();
    auto& gameRules = level.getGameRules();
    if ((*gameRules.mGameRules)[static_cast<int>(GameRules::GameRulesIndex::DoMobSpawning)].mValue->boolVal) {
        int randomValue     = random.nextIntInclusive(0, 1999);
        int difficultyValue = static_cast<int>(level.getDifficulty());
        return randomValue < difficultyValue;
    }
    return false;
}

C. Finding the spawn position and spawning:

C++
void PortalBlock::trySpawnPigZombie(
    ::BlockSource&    region,
    ::BlockPos const& pos,
    ::PortalAxis      axis
){
Vec3 _pos = pos;
    while (_pos.y-- > 1) {
        if (region.canProvideSupport(_pos, 1, ::BlockSupportType::Any)
            // && !region.isSolidBlockingBlock(_pos.x, _pos.y + 1, pos.z)
            // This is the check in the source, but as far as I know no solid block
            // fails to support the block above it, so this check is entirely redundant.
        ) {
            if (axis == PortalAxis::Z) {
                _pos.x += 1.5f;
                _pos.z += 0.5f;
            } else if (axis == PortalAxis::X) {
                _pos.x += 0.5f;
                _pos.z += 1.5f;
            }
            _pos.y += 1.1f;
            ll::service::getLevel()->getSpawner().spawnMob(
                region,
                ActorDefinitionIdentifier("minecraft:zombie_pigman"),
                nullptr,
                _pos,
                false,
                true,
                false
            );
            return;
        }
    }
}
